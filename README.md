# Advanced Detection Engineering & Threat Hunting Portfolio

Welcome to my corporate Detection Engineering portfolio. This repository demonstrates a complete detection lifecycle: from attack simulation (Red Teaming) to telemetry collection, through to the writing and validation of the detection rule in multi-vendor configurations (Splunk SPL, Microsoft Sentinel KQL, and Sigma).

The entire project was developed within a controlled (**DetectionLab**) enterprise-grade environment consisting of a Domain Controller, Windows 10 client machines monitored via Sysmon and Windows Event Forwarding (WEF), and a central Splunk instance (Logger).

## Performance Metrics & Validation

### Testing Methodology (Lab Verification)

Instead of relying on theoretical metrics, every rule in this repository has been empirically tested in an isolated environment:

* **True Positives (TP):** Generated by simulating real attacks using custom scripts and modules from **Atomic Red Team**. All 17 atomic rules successfully triggered their respective alerts.
* **False Positives (FP) e Tuning:** During the baseline phase, rules such as `T1070.001` (Clearing Event Logs) generated alerts due to legitimate IT maintenance scripts. The query was tuned by excluding the specific service account to eliminate false positives.

## ⚙️ The Detection Engineering Lifecycle

Every single rule in this repository has been developed and tested following a rigorous operational lifecycle. This ensures that the detections are not merely theoretical but applicable in a real-world enterprise environment (SOC).

```mermaid
graph LR
    A[🔴 1. Attack] -->|Atomic Red Team| B[📡 2. Telemetry]
    B -->|Sysmon / Event Logs| C[🛠️ 3. Detection]
    C -->|SPL / KQL / Sigma| D[🚨 4. Alert]
    D -->|SIEM Dashboard| E[🛡️ 5. Triage]
    E -->|Playbooks / CyberChef| F[✅ 6. Validation]
    
    style A fill:#3b1c1c,stroke:#d41f1f,stroke-width:2px,color:#fff
    style B fill:#1c2b3b,stroke:#0877a6,stroke-width:2px,color:#fff

    style F fill:#1c3b3b,stroke:#00a6a6,stroke-width:2px,color:#fff
```

1. **Attack:** Controlled simulation of the adversary through scripts or manual execution of MITRE techniques.
2. **Telemetry:** Verify that the infrastructure (WEF/Sysmon) has actually generated and forwarded the logs (EventID).
3. **Detection:** Write and optimize the query to isolate malicious behavior while minimizing false positives.
4. **Alert:** Configuring alarm parameters (Severity, Confidence, MITRE Mapping).
5. **Triage:** Drafting of the operational playbook containing instructions for the Level 1 (L1) analyst.
6. **Validation:** Stress-test the rule against the baseline to calculate metrics such as Precision and Recall.

## Architecture of the Validation Laboratory

The data flow follows a rigorous, centralized architecture to ensure that no telemetry is lost during attack phases:


\(\text{Atomic Red Team / Attaccante} \longrightarrow \text{Windows Endpoint (Sysmon/Security Log)} \longrightarrow \text{Windows Event Forwarder (WEF)} \longrightarrow \text{Splunk Forwarder} \longrightarrow \text{Splunk Enterprise (SIEM)}\)

1. **Attack Generation:** Tests are run programmatically using `Invoke-AtomicTest` or established OS commands.
2. **Telemetry Collection:** Advanced Windows auditing (Process Creation 4688 with CommandLine enabled) is enabled, combined with an optimized Sysmon configuration (based on SwiftOnSecurity).
3. **Log Forwarding:** Logs are centralized via WEF and indexed in Splunk under the `wineventlog` and `sysmon` indexes.

## Repository Structure

* `detections/`: It contains the logic and detailed definitions of SPL queries for Splunk.
* `kql/`: Repository of rules converted and optimized for **Microsoft Sentinel**.
* `sigma/`: Rules in the standard **Sigma (YAML)** format for maximum portability.
* `validation_reports/`: The 10 detailed reports containing the commands executed, the analysis of Event IDs, and the validation screenshots taken directly from the SIEM.
